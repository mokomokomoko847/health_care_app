# 共通要件

## プロジェクト名

楽ちん報告アプリ（仮）

## 1. アプリの目的

診察時に、お医者さんへ生活状況を説明する手間を減らすための
シンプルな健康ログアプリをFlutterで開発する。

今回開発するのは「プロトタイプ1（MVP）」である。

将来的には蓄積したデータをAI研究などへ活用する構想があるが、
AIによる予測・診断・合併症の予兆検知などは今回実装しない。

## 2. 開発技術

- Framework: Flutter
- Language: Dart
- 対象: スマートフォンアプリ
- 開発段階: Prototype 1 / MVP
- データ保存には Firebase を採用する。
- ユーザー認証には Firebase Authentication を使用する。
- 血糖値、測定日時、食前・食後、メモなどの記録データの保存には Cloud Firestore を使用する。

- Firebase プロジェクトは health_care_app 用として新規作成する。
- 食事写真の撮影・選択・記録への紐付け・表示・変更・削除・永続保存はMVPの対象とする。
- 写真ファイルは Cloud Storage for Firebase で管理し、Cloud Firestore に本人の記録と写真ファイルの参照を保存する。アプリ再起動後も写真を取得・表示できることを完成条件に含める。
- Cloud Storage for Firebase の採用理由は、ユーザー指定により食事写真も Firebase で永続管理するためである。
- Cloud Storage for Firebase は Blaze プランが必要なため、課金設定の有効化はユーザー確認後に行う。ドキュメントでの採用は課金設定の有効化を許可するものではない（[公式資料](https://firebase.google.com/docs/storage/flutter/start)）。
- 食事写真は保存対象の記録と紐付け、各写真がどの記録に属するか識別できるようにする。
- 既存 SQLite データは Firebase へ自動移行しない。
- Firebase への移行作業時に、既存 SQLite データを無断で削除しない。
- SQLite の削除が必要になった場合は、既存データの有無を確認してから実施する。

### セキュリティ方針

独自の API サーバーを認証・アクセス制御のために追加せず、以下の4つを組み合わせる。

1. Firebase Authentication：ユーザー認証を行う。画面の利用条件とメールアドレス確認は login.md に従う。
2. Firebase Security Rules：Cloud Firestore と Cloud Storage 側で、認証済みかつメールアドレス確認済みの本人にだけ記録・写真・訂正履歴の操作を許可する。画面上の操作制限だけに依存しない。
3. Firebase App Check：正規のアプリ・端末からのリクエストか検証し、不正クライアントによるバックエンドへのアクセスを抑制する。Authentication や Security Rules の代替にはしない。
4. テスト・監視：アクセス制限をテストし、運用中も拒否されたリクエストや不自然な利用量を確認する。テストの詳細は ../../test/SKILL.md を正とする。

- Security Rules では本人の記録・写真の保存・取得・更新・削除と、本人の訂正履歴の作成・取得を許可する。訂正履歴単独の更新・削除は許可せず、記録全体の削除に伴う削除のみ許可する。
- データの必須項目・型・入力範囲・変更可能な項目も Firebase 側で検証する。具体的な入力条件は各画面の要件定義を参照する。
- App Check は Cloud Firestore と Cloud Storage に適用する。公開前に正規の実機からのアクセスを確認し、両サービスで強制適用を有効にして、有効な App Check トークンがないリクエストを拒否する。
- 開発・テスト用の App Check デバッグ設定を本番アプリに含めない。
- Firebase コンソールで App Check のリクエスト指標と Firestore・Storage の利用量を確認できる状態にする。正規アクセスの拒否や不自然な利用量が見られた場合は原因を調査し、必要な設定を見直す。
- 記録内容・写真・パスワード・認証トークンを監視用ログに出力しない。
- この組み合わせも、アプリの改ざんや情報漏洩を100%防止する保証にはならない。App Check は不正アクセスを抑制する機能として扱い、ルールのテストと監視を継続する（[公式資料](https://firebase.google.com/docs/app-check)）。

### 保存・更新・削除の共通方針

- オンラインでのみ保存・更新・削除を実行する。オフラインでは実行せず、再接続後の自動送信や保留書き込みも行わない。
- Firebase 側で対象の記録・写真・必要な訂正履歴の処理がすべて成功した場合のみ完了とする。
- 成功以外は新規記録や編集内容を確定しない。失敗した更新・削除では、最後に正常保存された記録・写真・訂正履歴を保持する。
- 複数サービスをまたぐ処理は一部だけを完了扱いにしない。写真の準備後に記録の確定に失敗した場合は、準備した写真を破棄する。必要な後始末を完了するまで処理完了とはしない。
- 結果が不明な場合も成功扱いにせず、Firebase 側の結果を確認する。再試行で同じ記録や訂正履歴を重複作成しない。
- 処理中は重複実行を防止する。失敗時は入力内容を保持し、Firebase のエラーコードに対応する日本語のエラーメッセージをエラーダイアログで表示する。
- オフライン時は「通信できません。接続を確認して、もう一度お試しください。」と表示する。未対応のエラーコードは「処理に失敗しました。もう一度お試しください。」と表示する。

ただし以下を優先すること。

1. 可能な限り無料（0円）
2. プロトタイプとして実装が複雑になりすぎない
3. Flutterとの相性が良い
4. アプリ再起動後もデータを保持できる
5. 将来的にデータ構造を拡張しやすい

有料サービスが必要になる場合は、勝手に導入せずHumanへ確認すること。

## 3. Prototype 1で実装しないもの

以下は今回のMVPから明確に除外する。
- AIによる予測
- AIによる診断
- 合併症の予兆検知
- その他、Prototype 1の完成に不要な高度な機能

これらをCodexの判断で追加実装しないこと。

## 4. Prototype 1の完成条件

以下がすべて動作すればPrototype 1完成とする。

- 同じ画面内で「新規登録」と「ログイン」を切り替えられる
- メールアドレスとパスワードで新規登録でき、登録・認証とメールアドレス確認の完了後にカレンダーが表示される
- メールアドレスとパスワードでログインできる
- ログイン成功後、メールアドレス確認済みの場合はカレンダーが表示される
- 有効な認証状態を保持し、メールアドレス確認済みの場合、起動時にカレンダーが表示される
- カレンダーのボタンから記録入力画面へ遷移できる
- 日付入力で未来日を選択・手入力できない
- 記録がある日付をタップすると、その日の詳細画面が表示される
- 血糖値を入力できる
- 血糖値の入力ルール（整数・0〜600）が機能する
- 現在日時が初期値として自動取得される
- 日時をユーザーが変更できる
- 「食前」「食後」を選択できる
- メモを入力できる
- 食事写真をカメラで撮影できる
- 端末内の既存写真を選択できる
- 写真を最大3枚扱える
- カレンダーから新規記録を追加でき、Firebase への保存成功後はカレンダー画面へ戻る
- カレンダーから日付を選択できる
- 選択した日の記録を確認できる
- 同じ日の複数記録を確認できる
- アプリを再起動しても保存データが残っている
- 各画面の要件定義に記載された必須要件をすべて満たす。詳細な入力条件・操作条件は各画面の要件定義を正とする。
- メール確認待ち・確認状態の再確認・確認メール再送ができ、未確認ユーザーは認証後の画面を利用できない
- パスワード再設定メールからアプリ内で新しいパスワードを設定でき、手動でログイン画面へ戻ってログインできる
- カレンダーからログアウトでき、ログアウト後は認証後の画面へ戻れない
- 記録がない今日・過去の日付でも詳細画面と空状態を表示できる
- 詳細画面内で保存済み記録を編集・削除でき、記録入力画面へ遷移せず操作を完了できる
- 血糖値・測定日時の訂正履歴を保持・閲覧でき、記録が存在する間は履歴を編集・削除できない
- 写真を Firebase で永続管理し、再起動後も取得・表示・変更・削除できる
- メモの上限、未保存時の確認、未来日時の制限が機能する
- オフラインでは保存できず、失敗時は内容を確定せず日本語のエラーダイアログを表示する
- 記録の追加・編集・削除後に、詳細一覧とカレンダーの記録状態が更新される
- 上記のセキュリティ方針を満たし、Security Rules の許可・拒否テスト、App Check の強制適用の動作確認、監視指標の確認が完了している
